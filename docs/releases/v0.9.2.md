# Browser Pilot 0.9.2

> **Post-release correction (2026-08-11):** real Chrome validation showed that
> 0.9.2 retained the right mapping but reused it through the nonexistent
> `Target.createTarget.windowId` parameter. Chrome silently ignored that field
> and could place the Agent's next tab in a user window. 0.9.4 corrects this by
> reusing an owned target with `window.open` and verifying the exact resulting
> window before adopting it.

Browser Pilot 0.9.2 attempted to stop a Workspace losing the window it opened.
A dropped browser connection left that window open in Chrome while the Broker
forgot it, so the next command built another one and abandoned the first.

## Intended window behavior

The Broker keyed its window on the ManagedTabSet, which is bound to a
ProfileContext — and a `profileContextId` is valid only for its connection
generation. After a reconnect the lookup could not hit, whatever the Broker
still remembered.

The key is now Chrome's own browser-context id, which belongs to the Profile
rather than to the debugging session and therefore outlives the connection,
scoped by Workspace so separate Agents keep separate windows. Where Chrome
reports no context the behaviour is unchanged.

Two effects were intended. Orphaned windows holding a lone `about:blank` stop
accumulating. And because a managed tab can only land in a window the user is
working in while bootstrapping a new one, keeping the window makes that
possibility rarer without any machinery aimed at it.

## Upgrading

No protocol change; 0.9.2 speaks `1.4` as 0.9.1 does. Nothing in the CLI
surface or the skill moved.
