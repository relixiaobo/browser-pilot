# Browser Pilot 0.9.4

Browser Pilot 0.9.4 corrects the window-reuse fix released in 0.9.2. After a
same-process browser reconnect, Chrome could leave the original managed window
open and place the Agent's next tab in a window the user was working in. 0.9.3
inherited the same behavior.

## Reconnects reuse an owned target

The 0.9.2 implementation retained Chrome's window ID, then passed it back as
`Target.createTarget.windowId`. That parameter does not exist. Chrome silently
ignored it and selected a window itself, while the test fixture implemented the
unsupported routing behavior and made the regression look fixed.

The Broker now retains both the verified window ID and the raw target IDs of
the pages it owns. After a reconnect to the same Chrome process it:

1. resolves an owned page that still belongs to the expected Profile and exact
   window;
2. re-adopts that page into the replacement managed-target janitor;
3. opens a sibling tab from an isolated world with `window.open`;
4. verifies the new tab's Profile context and exact Chrome window before
   exposing it to the Agent.

If the retained page or window no longer exists, the stale mapping is discarded
and normal managed-window bootstrap creates a replacement.

## Cleanup crosses reconnect generations

Reconnecting invalidates the Broker's public target records, but Chrome keeps
the underlying pages alive. Workspace release now also closes the raw owned
targets retained from earlier connection generations, so a reconnect cannot
turn them into abandoned tabs.

## Validation uses Google Chrome

The fixture now models Chrome's real `Target.createTarget` contract and rejects
the nonexistent window selector. A Google Chrome regression creates separate
managed and decoy windows, kills the managed-target janitor, reconnects the same
Broker to the same Chrome process, and verifies that the next managed target
returns to the original managed window. It also verifies that no orphaned
`about:blank` target remains.

## Upgrading

No protocol change; 0.9.4 speaks `1.4` as 0.9.3 does.

An already-running 0.9.3 service still executes the old code after a newer
executable is installed. Stop it with the matching installation as described in
the 0.9.3 release notes, then confirm both `bp --version` and `bp status` report
0.9.4.
