# Browser Pilot v0.6.0 Hardening Plan

Status: **Implemented and released as v0.6.0 on 2026-07-31**
Baseline: `main` @ `7b1db91` (v0.5.1)
Release: `v0.6.0` @ `691cb70` ([GitHub Release](https://github.com/relixiaobo/browser-pilot/releases/tag/v0.6.0))

Revision notes (v2): incorporates an external design review. Major changes:
phases reordered so the CI safety net lands before hardening; daemon
single-instance ownership redesigned to remove TOCTOU; endpoint
authentication rebuilt around an explicit threat model; release-job order
changed to draft-release → npm → publish; idempotency fix promoted into the
correctness phase; every item now carries a compatibility classification.

Revision notes (v3): second review round. Session identity now derives via
HMAC keyed by the daemon token — a broker-assigned random id would break

demoted from a requirement to a technical spike (Node exposes no API for

(deadlock with the CLI's lock-holding window); the release workflow gains
re-run/idempotency semantics; `[compatible]` redefined so defect fixes

Revision notes (v4): third review round. Mixed-version policy fixed to
fail-closed (baseline `validateDaemon` throws before any shutdown logic —
a live daemon is never auto-replaced); 2.4 escaping relocated to where
structural lines are actually produced (the CLI human renderer; JSON
values stay raw); the npm artifact gets one authoritative packed tgz whose
recorded SHA-512 is the re-run identity, with the publish state machine
made script-testable; the daemon lifetime lock binds process start
identity to survive pid reuse; open decisions closed: `engines.node >=22`,
iframe/subframe fixes (6.7) deferred out of v0.6.0; HMAC input gains
domain separation and the token/locator/reload contract is pinned down.

Revision notes (v5): fourth review round, executability fixes. The
authoritative npm tgz now lives on the draft release (workflow artifacts
are immutable and not visible across runs), with an explicit
release-already-public no-op state; credential change now discards the
whole client construction instead of transparently retrying (the HMAC

desync identity and mint duplicate connections); the lock-reclamation
fallback fails closed when start identity is unobtainable and the pid is
alive; `/health` gets an explicit field allowlist derived from what
shipped v0.5.1 consumers actually read; the new-CLI remediation no longer
says bare `bp disconnect` (it would exit at the protocol check); the
`mkdtemp` call form is corrected; 1.5 marked plain [breaking].

Revision notes (v6): fifth review round. The 4.3 test matrix is
synchronized with the v5 contract — added cases for credential change
during initialize (client rebuilt, no old-session/new-token pairing),
no transparent replay of dispatched mutating RPCs, exact `/health`

## Goal

Close the correctness, security, and CI gaps found in the 2026-07 full
project review, with **no undeclared breaking change**. Behavior changes are
allowed, but each work item is classified up front:

- **[compatible]** — no consumer migration required: schemas stay
  backward compatible, and behavior changes only where current behavior is
  a defect against the documented/intended contract.
- **[additive]** — new fields, new error codes, new commands; existing
  consumers unaffected.
- **[breaking]** — observable behavior or wire contract changes; requires a
  version bump, a skill-doc update, and a release-notes entry in the same PR.

The public contract is: the `bp` CLI surface, its JSON output schemas, the
error `code` set (`src/protocol/errors.ts`), and the skill guidance
(`plugin/skills/browser-pilot/**`). The CLI↔daemon HTTP transport is private
but versioned (`BROKER_RPC_VERSION`, `src/client.ts:27`); any change to its
wire shape (including headers) bumps that version and defines the mixed
old/new behavior explicitly.

## Ground rules for the implementing agent

- Tests that drive Chrome **through bp/daemon** must use the isolated
  fixture (`scripts/isolated-chrome-fixture.mjs`, guarded by
  `tests/bp.ts`). Tests that launch Chrome directly (playwright
  `chromium.launch`) must use an isolated temporary profile and must never
  attach to or mutate the user's real Chrome profile.
- Every fix lands with a regression test that fails on the old code.
- One PR per numbered work item unless the item says otherwise.
- Do not bump broker protocol versions unless the wire contract actually
  changes; items that do are marked.
- Phases are ordered by dependency, not importance: Phase 1 builds the CI
  safety net that protects everything after it. Do not start Phase 2+ items
  on a surface whose tests Phase 1 has not yet put under CI, unless the item
  itself adds the coverage.

## Phase 1 — CI safety net and test portability

Rationale: the three Playwright projects (109 tests — the only end-to-end
coverage of `bp connect → daemon → Chrome`) and the Windows code paths
currently run only on the maintainer's machine. Land this first so every
subsequent hardening change is actually gated.

### 1.1 Declare `playwright`, split real-Chrome tests out of `test:unit` — [compatible]

**Problem.** `tests/page-primitives.test.mjs:18`,
`tests/editable-actions.test.mjs:17`, and
`tests/browser-capability-fixtures.test.mjs:146-148` launch real Chrome
(`chromium.launch({ channel: 'chrome' })`) inside the "unit" suite with no
skip guard, and import `playwright`, which is not in `package.json`
(resolved via hoisting from `@playwright/test`).

**Change.**
1. Add `playwright` to devDependencies.
2. Move the three files to a new `test:browser` script; `test:unit` becomes
   Chrome-free.
3. `test:browser` detects Chrome availability: skip locally when missing,
   fail when `CI` is set.

### 1.2 Run the Playwright gates in CI — [compatible]

**Change.** Add a CI job (ubuntu) running
`npx playwright test --project core --project compat --project network`
plus `npm run test:browser`, after the unit job. The isolated fixture is
already `--headless=new` and ubuntu runners ship Chrome. Upload the
Playwright report on failure. Add `timeout-minutes` to all jobs in both
workflows. Add a `concurrency` group with `cancel-in-progress: true` to
`ci.yml` **only** — never to `release.yml` (a cancellation point between
irreversible publish steps is worse than a queued duplicate run).

Note: `setup-node` already caches npm (`.github/workflows/ci.yml:18`); no
extra cache step needed.

**Acceptance.** CI green on a no-op PR; a deliberately broken selector in a
spec (local check, not committed) fails the job.

### 1.3 Test-suite portability, then a Windows CI leg — [compatible]

**Problem.** The Windows named-pipe branch (`src/paths.ts:39-57`) and the
unit suite have never executed on Windows, yet signed Windows binaries
ship. Blocking issue: the existing tests are not Windows-portable — they
hardcode `/tmp`-style paths via `mkdtemp` defaults, use `SIGKILL`
semantics, and create symlinks.

**Change.** Two PRs:
1. Portability pass over `tests/*.test.mjs` and helpers: route real
   temp-resource creation through
   `mkdtemp(join(os.tmpdir(), 'browser-pilot-'))` (note: passing
   `os.tmpdir()` bare would append the random suffix to the temp dir
   path itself instead of creating a child directory) — the "no literal
   `/tmp`" check applies only to paths actually created on disk;
   pure path-parsing cases that intentionally use Unix-style strings as
   inputs (e.g. `tests/broker-locator.test.mjs:27`) stay as they are,
   scoped to Unix where the asserted behavior is platform-specific.
   Replace SIGKILL-dependent assertions with portable process-kill
   helpers, gate symlink-dependent fixtures (skip-with-reason on Windows
   or use junction-safe equivalents), normalize path separators in
   assertions.
2. Add a `windows-latest` CI leg running `test:unit` (Chrome-free after
   1.1), `tsc --noEmit`, and `test:distribution`. Fix the Windows-only
   failures this surfaces (there will be some — spawn semantics, named-pipe
   paths). Optionally add `macos-14` for `test:distribution` parity with
   release.yml.

### 1.4 Fail-early manifest sync check — [compatible]

**Change.** Add `npm run release:check-version` to `ci.yml` so desync of

`package-lock.json` fails at PR time instead of tag time. Make the
`version` npm hook (`package.json:20`) `git add` the files it rewrites so a

### 1.5 Lint gate and Node engines decision — [breaking]

**Change.** Add a lint config (biome or eslint flat config — pick one,
minimal rules: no-unused, no-floating-promises, import hygiene) and a CI
step, plus one bulk-fix PR.

Engines: **decision — raise `engines.node` to `>=22`.** Node 18 and 20
are both EOL at the time of writing, and the npm distribution targets

stays on Node 22.

## Phase 2 — Correctness and safety fixes

Recommended order within the phase: 2.1 → 2.2 → 2.3 → 2.4/2.5 → 2.6/2.7 →
2.8/2.9/2.10 (2.7 depends on 2.6's error-classification work).

### 2.1 Make `--request-id` idempotency survive real retries — [compatible]

Promoted to this phase: the current behavior violates the recovery contract
the v0.5 README/skill already promise, so this is a correctness bug, not a
hardening extra.

**Problem.** `commandId`/`idempotencyKey` derive from requestId **plus a
per-process monotonic `commandSequence`**
(`src/compatibility-broker-client.ts:177-188,390-403`). A retrying CLI
process restarts the sequence at 1, and preamble calls like `ensureTarget`
(`src/compatibility-broker-client.ts:290-302`) depend on live browser
state, so sequences misalign easily; the mutating command then gets a fresh
commandId and broker dedup never fires — double execution.

**Change.** Derive the idempotency key for mutating tool calls from
`requestId + toolName + hash(canonical-JSON(args) + resolvedTargetId)`.
Canonical JSON: sorted keys, no insignificant whitespace, stable number
formatting — write one helper, unit-test it. Including the resolved
targetId prevents a retry that lands on a different tab from silently
deduping against the original. Keep sequence/uuid for display commandIds of
non-mutating preamble calls. Verify against the dedup logic in
`src/services/broker-runtime.ts`; this should be client-side derivation
only — bump protocol only if the wire contract actually changes.

**Tests.** Contract test: run `bp --request-id X open <url>` against the
fake daemon, kill after dispatch, rerun; assert the broker receives the
same idempotency key and dedups. Assert two *different* commands sharing a
requestId do NOT collide. Assert a retry resolving to a different targetId
does not dedup.

### 2.2 Daemon single-instance ownership (atomic, no TOCTOU) — [compatible]

**Problem.** `cleanup()` (`src/daemon.ts:57-62`) unconditionally unlinks
the socket; startup (`src/daemon.ts:46,53-55`) unlinks the socket and
overwrites pidFile/locator **before `main()` even runs**. The daemon does
not participate in any lock — mutual exclusion lives only in the CLI's
`connectDaemon` (`src/session.ts:109-167`). A stale daemon exiting deletes
the live daemon's socket with no self-healing path. A probe-then-unlink fix
would merely shrink the race, not close it.

**Change.** The daemon itself acquires atomic single-instance ownership:
1. On startup, before touching any shared file, the daemon acquires a
   **lifetime singleton lock** (atomic create-exclusive lock file with
   owner identity, held until exit — reuse the identity/atomic-write
   machinery in `src/broker-locator.ts`). This must be a **new, separate
   lock file** (e.g. `daemon-owner.lock`), never the existing startup
   lock: the CLI holds the startup lock across daemon spawn until the
   health check completes (`src/session.ts:109`), so a daemon waiting on
   that same lock would deadlock with its own launcher.
2. The lock's owner record must bind a verifiable process identity, not a
   bare pid: baseline liveness is only `kill(pid, 0)`
   (`src/broker-locator.ts:367`), so a recycled pid would keep a dead
   daemon's lock alive forever. Record pid **plus process start time**
   where obtainable (Linux `/proc/<pid>/stat` field 22, macOS
   `ps -o lstart= -p`, Windows `Get-CimInstance Win32_Process`
   CreationDate) and treat a start-time mismatch as "owner dead". Where
   start identity is unobtainable **and the owner pid is alive, fail
   closed — do not reclaim**: a real daemon that is temporarily blocked
   (long GC pause, saturated event loop) looks exactly like "alive but
   unresponsive", and a transient failure of the start-time query must
   not let a second daemon steal the lock. Exit with a distinct error
   carrying manual recovery guidance (inspect/stop the recorded pid, or
   use a separate `BROWSER_PILOT_HOME`). Automatic reclamation requires
   a dead pid or a provably mismatched start identity.
3. Only when the owner is dead by that definition is stale state (lock,
   socket, pidFile, locator) cleaned — and that cleanup happens under a
   fresh lock acquisition, not before it.
4. All destructive operations (socket unlink, pidFile/locator overwrite,
   cleanup on exit) execute only while holding the lock and only when the
   recorded identity matches the current process. Move the pre-`main()`
   unlinks behind the lock acquisition.

**Tests** (extend `tests/broker-startup-process.test.mjs` /
`tests/daemon-crash-cleanup.test.mjs`), five scenarios:
1. Second daemon started against the same home while the first is alive →
   refuses to start with a distinct error, first daemon unaffected.
2. First daemon SIGKILLed → next startup detects dead owner, cleans stale
   state, serves clients.
3. Stale daemon exiting (its `cleanup()` running late) does **not** remove
   the new daemon's socket; clients stay connected.
4. Lock held by a live pid that is **not** the original daemon (write a
   lock record with a live foreign pid and a mismatched start identity) →
   detected as dead owner and reclaimed; the unrelated process is never
   signaled.
5. Lock held by a live pid whose start identity cannot be read (simulate
   the query failing) → startup fails closed with the manual-recovery
   error; no reclamation, no second daemon.

### 2.3 Fix `adoptTarget` result validation — [compatible]

**Problem.** `src/managed-target-janitor-client.ts:128-132` throws unless
`adopted === 1`, but the janitor's adopt does transitive closure over popup
descendants (`src/managed-target-janitor.ts:99-127`) so `adopted` can be
> 1, and the `'owned'`-event race can make it 0. Both are successful
adoptions reported as `internal_error`.

**Change.** Extend the janitor's adopt response (private IPC protocol) to
report per-requested-id ownership: `{ owned: { [targetId]: boolean } }`.
The client checks that the requested id is owned; the count becomes
informational.

**Tests.** In `tests/managed-target-janitor.test.mjs`: adopt a target with
a tracked popup descendant (success, adopted > 1); adopt concurrently with
the `'owned'` auto-track event (success, adopted 0); adopt a nonexistent
target (failure preserved).

### 2.4 Escape page-derived text in structural output — [compatible]

**Problem.** The AX snapshot path interpolates raw accessible names/values
into the `[N] role "name"` line format
(`src/snapshot.ts:291-293,355-359`). A page can embed newlines in
`aria-label` to fabricate snapshot lines — including fake refs — and
mislead the consuming LLM. The DOM path normalizes whitespace
(`src/dom-snapshot.ts:363-365`) but nothing escapes quotes.

**Change.** The fix must land where structural lines are actually
produced. The production path returns structured `elements` over RPC, and
the **CLI human renderer** reassembles the `[N] role "name"` lines
(`emitObservation` and the read/search/find human branches,
`src/cli.ts:155` area); the snapshot-internal text assembly
(`src/snapshot.ts:355-359`) is a secondary producer — audit where its
output surfaces (evidence, hints) and fix those paths too. Concretely:
1. One shared serializer: escape via JSON-string semantics (quotes,
   backslashes, control characters, Unicode line/paragraph separators
   U+2028/U+2029), collapse remaining whitespace runs, cap length.
2. Apply it in every plain-text/structural renderer to page-derived
   fields: AX names, AX values, element titles, URLs, frame labels.
3. **JSON output keeps raw semantic values unchanged** — `JSON.stringify`
   already escapes control characters inside string literals, so JSON
   consumers cannot have line structure broken, and rewriting values
   would itself break the [compatible] classification.
Page text that is *content* (`bp read` body) may keep newlines; page text
inside a structural line must not be able to break line structure.

**Tests.** Fixture element with
`aria-label='"\n[99] button "Fake"'` (embedded quote + newline) — assert
the **human-format** output renders exactly one line for it, no ref `99`,
quote visibly escaped; assert the JSON output still carries the raw value
in the element field (schema unchanged). Repeat for a crafted
`document.title` and URL, and for any evidence/hint line built from page
text.

### 2.5 Isolated observation world with `exceptionDetails` checks — [compatible]

**Problem.** `PAGE_INFO` runs in the page's main world without checking
`exceptionDetails` (`src/snapshot.ts:142-147`, `src/page-scripts.ts:430`).
A page overriding `JSON.stringify` or throwing in a `title` getter breaks
observation with an opaque `JSON.parse` error, and can forge guidance
signals. The same exposure applies to the other observation scripts —
audit **all** `Runtime.evaluate` call sites in `src/snapshot.ts`,
`src/services/page-content-service.ts`, and the search/find paths of
`src/services/page-inspection-service.ts`.

**Change.** Introduce one cached observation isolated world per frame,
keyed by `{cdpSessionId, frameId}` and covering the **top frame** as well
as subframes (create via `Page.createIsolatedWorld`, cache the
executionContextId — mirroring what `src/services/frame-service.ts:203-211`
already does for subframes). Invalidation: the existing
context-destroyed/navigation hooks
(`src/services/browser-tool-service.ts:3279-3300`) only clear the *active*
frame's context — extend them to invalidate every cached entry for the
affected cdpSession/frame, not just the active one. Run all observation
scripts there; check `exceptionDetails` and map failures to a structured
error. `bp eval` intentionally stays in the main world — it is
the escape hatch for page-context execution; say so in its help text.

**Tests.** Fixture page overriding `JSON.stringify`, defining a throwing
`document.title` getter, and monkeypatching `document.querySelector`;
assert `bp snapshot`, `bp read`, `bp search`, `bp find` all still succeed.

### 2.6 CDP error fidelity and liveness — full chain — [compatible]

**Problem.** Three gaps, and the fix must cover the whole production chain
(`BrowserToolService → ManagedTargetJanitorClient → janitor → CDPClient`),
not just `cdp.ts`:
- `connect` (`src/cdp.ts:30`) has no handshake timeout; Chrome's
  authorization flow can hang the WS handshake forever, and the daemon
  caches the pending promise (`src/daemon.ts:354-355`) so all later
  connects reuse the hang.
- No keepalive: after sleep/network change the state stays `connected` on
  a half-open socket; every request waits the full 30s
  (`src/cdp.ts:119-122`).
- Error fidelity is lost twice: `cdp.ts:76-77` drops CDP `code`/`data`,
  and even if preserved, the janitor forwards only `message`
  (`src/managed-target-janitor.ts:150` response path) and the client
  rebuilds a plain `Error` from the message string
  (`src/managed-target-janitor-client.ts:229`). Upper layers are forced to
  treat every failure as `stale_ref` (`src/snapshot.ts:424-439`).

**Change.**
1. `CDPClient`: accept injectable timing parameters
   (`handshakeTimeoutMs`, `pingIntervalMs`, `pongTimeoutMs`) so unit tests
   run in milliseconds. Defaults: handshake ~8s with a distinct error code
   (so the daemon can report "authorization pending" instead of hanging —
   align with the probe heuristic at `src/chrome.ts:276`); ping 15s, 2
   missed pongs → run the existing disconnect path.
2. Preserve CDP `code`/`data` on thrown errors in `cdp.ts`.
3. Extend the janitor IPC protocol (same private-protocol change as 2.3 —
   coordinate the two items) to carry `{ code, message, data? }` for
   errors; rebuild typed errors client-side.
4. Update `src/snapshot.ts:424-439` to branch on the structured code.

**Tests.** Unit tests with fast injected clocks against a fake CDP server:
handshake-never-completes → distinct code within timeout; pings
unanswered → disconnected without 30s wait; CDP error round-trips
code/data through the janitor client. One slower integration case in
`tests/daemon-reconnect.test.mjs` with near-default timings.

### 2.7 Chrome discovery: liveness, process match, async, diagnosis — [compatible]

Depends on 2.6 (the distinct handshake-timeout code feeds the diagnosis
split).

**Problem** (`src/chrome.ts`):
- Lock-file existence is treated as "running" (`src/chrome.ts:226-228`);
  Linux `SingletonLock` survives SIGKILL, Windows lock files persist after
  clean exit → false "running", and a stale `DevToolsActivePort` then
  yields a connect failure the daemon misdiagnoses as
  `browser_not_authorized` (`src/daemon.ts:390-414`).
- The Linux `ps` fallback matches `google-chrome[-stable]` names but the
  real process is `/opt/google/chrome/chrome`
  (`src/chrome.ts:230-239`) — never matches.
- `readRunningCommands` is `execFileSync` (`src/chrome.ts:207-220`) inside
  the daemon's 2s refresh (`src/daemon.ts:458-484`) — blocks the event
  loop.

**Change.**
1. Linux: parse `SingletonLock`'s `hostname-pid` target, verify with
   `process.kill(pid, 0)`. Windows: never trust lock-file existence; use
   process enumeration or an exclusive-open attempt.
2. Process matching must bind to the **profile/data-dir**, not "any Chrome
   is running": match the candidate's `--user-data-dir` (or default
   profile path) in the command line, so an unrelated Chrome instance
   doesn't validate a stale endpoint. On Windows, `tasklist` exposes only
   process names — read command lines via PowerShell
   `Get-CimInstance Win32_Process` (select `ProcessId, CommandLine`;
   `wmic` is deprecated/removed on current Windows).
3. Async process enumeration (promisified `execFile`).
4. Daemon connect-failure diagnosis split: ECONNREFUSED/stale-port →
   "browser not running / stale debugging port" remediation;
   handshake-timeout (2.6's code) → authorization remediation. Stop
   mapping every failure to `browser_not_authorized`.

**Tests.** Extend `tests/chrome-discovery.test.mjs`: stale `SingletonLock`
pointing at a dead pid; live pid with mismatched data-dir; assert
remediation codes for each daemon diagnosis branch.

### 2.8 Make `bp wait` side-effect free — [additive]

**Problem.** The `--url/--text/--selector` wait paths call `ensureTarget`
(`src/cli.ts:675`), creating an `about:blank` managed tab when none is
selected. A wait must not mutate browser state.

**Change.** Add a read-only `selectedTarget()` resolution path on the
compatibility client (do not reuse `ensureTarget`). With no selected tab,
fail fast. Contract decision required first: add a new error code
`no_selected_tab` to `src/protocol/errors.ts` (**additive** — new code,
document in `plugin/skills/browser-pilot/references/recovery.md` and
`async.md`) rather than overloading an existing code.

**Tests.** `tests/cli-broker-adapter.test.mjs`: `bp wait --text x` with no
selected tab → `no_selected_tab`, and no target-creation RPC observed by
the fake daemon.

### 2.9 Snapshot cost guards on large pages — [additive]

**Problem.** Output is budgeted but computation is not:
- After budget exhaustion the DOM-only scan still computes
  `domElementName/domElementValue` per candidate before `addElement`
  discards them (`src/snapshot.ts:330-347`).
- The per-candidate ancestor/lineage walk (`src/dom-snapshot.ts:287`) and
  `descendantText` (`src/dom-snapshot.ts:377`, up to 10k nodes per
  candidate) are near-quadratic on large pages.

**Change.** Short-circuit candidate processing once the budget is
exhausted; compute name/value lazily on admission. Memoize the ancestor
walk (per-node cached lineage flags) and cap cumulative descendant-text
work per snapshot. Record hitting the cap as a new truncation reason
`work_limit` alongside the existing reasons in observation metadata
(**additive**: new enum value — document it wherever truncation reasons
are listed in the skill references).

**Tests.** Deep-DOM fixture (thousands of nested clickables) asserting the
scan visits bounded work — expose a test-only counter hook rather than
relying on wall-clock, plus one loose wall-time bound to catch gross
regressions. Truncation metadata stays intact.

### 2.10 Truthful error propagation and janitor edge behavior — [compatible]

**Problem.**
- `resumeCompatibility` swallows every error except
  `protocol_incompatible` into `null`
  (`src/compatibility-broker-client.ts:447-450`); lease limits and broker
  internal errors surface as "browser_disconnected + install remediation"
  (`src/cli.ts:418-433`).
- Janitor stdin framing kills the whole session (closing all managed tabs)
  on a single >64KB request (`src/managed-target-janitor.ts:54,261-275`).
- `stopWorker(cleanup=false)` sends SIGTERM but the janitor's handler runs
  full cleanup against a dead connection for up to 5s
  (`src/managed-target-janitor-client.ts:320-325`,
  `src/managed-target-janitor.ts:216`).
- Capacity-full adopt closes the tab it was asked to adopt
  (`src/managed-target-janitor.ts:64-67`).

**Change.** Pass through structured broker errors from resume (allowlist
by code if needed) so `bp status` and failures reflect the real fault.
Oversized janitor frames: the receiver cannot extract a request id from a
frame it refuses to parse, so enforce the size limit at the **sender**
(`ManagedTargetJanitorClient` fails the call locally before writing) and
give the receiver a discard-and-resync rule (skip bytes to the next
newline delimiter, emit a protocol-error event, keep serving) instead of
`finish(true)`. Add an explicit no-cleanup shutdown message for the
`cleanup=false` path; capacity-full adopt fails the request without
closing the target.

**Tests.** One regression test per behavior in the existing janitor and
adapter test files.

## Phase 3 — Legacy surface removal

### 3.1 Remove the legacy daemon API and dead client code — [compatible]

**Problem.** Two API generations coexist. Current: `POST /broker/rpc`
(`src/daemon.ts:609`) → `MemoryBrokerRuntime`. Legacy: `/cdp`, `/auth`,
`/discovered`, `/dialogs`, `/net/*` (`src/daemon.ts:634-833`) plus
module-level state (`src/daemon.ts:89-170`) and a CDP event bridge
(`src/daemon.ts:490-574`), with matching `DaemonClient` methods
(`src/client.ts:107-254`) that have **no production callers**. `/cdp` lets
any same-user process send arbitrary CDP commands, bypassing the entire
workspace/lease/capability model, and pollutes global `activeSessionId`
(`src/daemon.ts:637`). Removing this surface eliminates the daemon's worst
exposure before Phase 4 protects what remains.

## Phase 4 — Daemon endpoint hardening

### 4.1 Threat model (decide before writing code)

The endpoint is a Unix socket at mode 0600 inside a 0700 directory
(`src/daemon.ts:842`, `src/broker-locator.ts:120-124`) or a Windows named
pipe (`src/paths.ts:52`). Be explicit about what a shared-secret token can
and cannot do:

**In scope (what this phase defends):**
- Cross-user access: already blocked on Unix by file modes; on Windows the
  named pipe currently relies on the default DACL — see 4.2 for the
  constraint and options.
- Sandboxed same-user processes (no filesystem read on the Browser Pilot
  home): a token they cannot read blocks pipe/socket access they might
  otherwise have.
- Accidental/confused-deputy calls from well-behaved same-user software
  that can reach the transport but has no business driving the broker.
- Session impersonation by *guessing*: `clientSessionId` is currently
  derived deterministically from clientKey+version
  (`src/compatibility-broker-client.ts:81-99`) — trivially predictable.

**Out of scope (documented, not defended):** a malicious process running
as the same OS user with filesystem access can read any shared secret this
design can store; defending that requires per-client credentials issued
through user interaction or an OS/host-provided boundary. Record this
explicitly in the platform spec (`docs/architecture/`) so nobody mistakes
the token for same-user malware protection.

### 4.2 Technical spike: Windows pipe access control — [decision required before 4.3]

Node's `net.Server.listen()` exposes no API to set a security descriptor
on a named pipe — only `readableAll`/`writableAll`, which *broaden*
access. A native addon would complicate the SEA standalone build. Before
starting 4.3, prototype and pick one:

1. A native/helper step that applies a current-user-SID ACL to the pipe
   (cost: native dependency in the SEA pipeline — measure it);
2. Accept the default pipe DACL and make the **token the primary Windows
   defense**, explicitly tightening ACLs on the state dir and token file
   at daemon startup (PowerShell `Set-Acl` / `icacls`);
3. Switch the Windows transport to loopback TCP + token (drops named
   pipes entirely; simplest code path, but binds a local port).

Record the decision and rationale in the platform spec. Option 2 is the
likely default if the spike finds option 1 impractical — it is consistent
with the 4.1 threat model, which already treats the token as the boundary
for processes that can reach the transport but cannot read the state dir.

### 4.3 Implementation — [breaking, private wire contract: BROKER_RPC_VERSION 2 → 3]

**Change.**
1. Daemon generates a random token at startup, stores it in the locator
   file — **the locator is the token file**: 4.2's option-2 ACL
   tightening targets the locator and its state dir, nothing else. Every
   endpoint **except `GET /health`** requires the token
   (`Authorization` header); reject otherwise with a structured error.
   Credential-change contract: do **not** transparently retry inside the
   transport. The HMAC session id is computed from the token before
   `initialize` runs (`src/compatibility-broker-client.ts:81-99,133`),
   so a token-reload-and-replay would send the new `Authorization` with
   the **old** HMAC session id — and the next CLI invocation, deriving
   the new HMAC, would then mint a second connection with its own
   connection-bound leases. On an auth rejection or broker identity
   mismatch: discard the entire client construction, re-read the locator
   once, recompute the HMAC session id, and restart from `initialize`.
   Never transparently replay an already-dispatched mutating RPC —
   recovery of those goes through the 2.1 request-id path. If the
   rebuilt client still fails, surface the structured error; no retry
   loops.
2. `/health` stays unauthenticated and read-only, with an **explicit
   field allowlist** — "minimal" is not a spec. The allowlist is derived
   from what shipped v0.5.1 consumers actually read, and dropping any of
   it breaks them: the version/identity set (`ok`, `brokerProtocol`,
   `serviceVersion`, `executableVersion`, `executableIdentity`,
   `brokerProcessIdentity` — the disconnect/ownership flow reads the
   identities, `src/compatibility-broker-client.ts:479`; without them
   `bp disconnect` can never stop the daemon) and the browser-selection
   summary (`browser`, `clients` — `assertBrowserSelection` runs against
   healthInfo before any protocol check, `src/session.ts:62`; without it
   `--browser` filters misreport). None of these are secrets under the
   4.1 threat model; the token never appears in `/health`. One audit
   item: `wsUrl` — if exposing the CDP websocket URL grants direct
   browser access beyond what transport reachability already implies,
   move it behind auth after verifying no v0.5.1 pre-protocol-check path
   reads it. Any state beyond the allowlist lives only in authenticated
   endpoints. Rationale for keeping `/health` open at all: v0.5.1's
   `healthInfo()` swallows request errors into `{ ok: false }`
   (`src/client.ts:115`), so if `/health` required auth, an old CLI
   could only ever report "alive but unresponsive"; open, its existing
   brokerProtocol check reports the incompatibility correctly.
3. Session identity: derive
   `clientSessionId = HMAC(daemonToken, encode(clientKey, executableVersion))`
   where `encode` is an unambiguous field encoding — length-prefix each
   field or join with `\0` (`clientKey + "\0" + executableVersion`) — so
   field boundaries cannot be shifted between the inputs. This replaces
   the predictable derivation
   (`src/compatibility-broker-client.ts:81-99`). Do **not** use a
   broker-assigned random id per CLI invocation: short-lived CLI
   processes rely on a stable session id to reuse their connection
   (`src/services/broker-runtime.ts:608`) and the leases bound to it
   (`src/services/broker-runtime.ts:826`); a fresh id per invocation
   would accumulate connections/leases and conflict with the agent's own
   prior control. HMAC keyed by the token is stable across processes and
   unguessable without the token; token holders are inside this phase's
   trust boundary by definition.
4. Bump `BROKER_RPC_VERSION` (`src/client.ts:27`) 2 → 3. Mixed-version
   policy is **fail-closed: a live daemon is never auto-replaced**. This
   matches baseline behavior — `validateDaemon` throws
   `protocol_incompatible` before any shutdown logic
   (`src/compatibility-broker-client.ts:406`), and existing tests assert
   a running Broker is not replaced. Matrix (both directions discovered
   via the open `/health`):
   - **New CLI + old daemon**: `/health` reports `brokerProtocol: 2`; the
     CLI reports the incompatible broker with upgrade remediation. The
     remediation must **not** say bare "run `bp disconnect`" — the new
     CLI's own disconnect exits at the protocol check before any
     shutdown logic (`src/compatibility-broker-client.ts:406`). It must
     instead direct the user to stop the old service with the
     **executable that started it** (`<old bp> disconnect`, honoring the
     existing executable-identity rules), or give explicit manual
     guidance: the recorded daemon pid to stop, or a separate
     `BROWSER_PILOT_HOME` for isolation. No automatic replacement, under
     any ownership condition.
   - **Old CLI + new daemon**: `/health` succeeds and reports
     `brokerProtocol: 3`; the old CLI's existing version check surfaces
     the incompatibility. Authenticated endpoints reject its tokenless
     requests with a structured error as a backstop.
5. Unix: create the socket under a restrictive umask so the listen→chmod
   window (`src/daemon.ts:840-843`) closes. Windows: apply the 4.2
   decision.

**Tests.** Adapter tests:
- No token / wrong token on an authenticated endpoint → structured
  rejection; `/health` without token → succeeds.
- `/health` response matches the allowlist **exactly**: assert the
  response's field set equals the allowlist — the token, `wsUrl` (if
  moved behind auth), and any other non-allowlisted field must not
  appear.
- Old-CLI-shaped flow (health, then tokenless RPC) → parseable upgrade
  error.
- HMAC session id stable across two CLI processes with the same
  clientKey — connection reused, no second connection in broker stats.
- Credential change during initialize: restart the fake daemon with a
  new token/identity between client construction and `initialize` →
  the client construction is discarded and rebuilt (new HMAC session id
  derived from the new token; exactly one connection in broker stats
  afterward), and no request ever pairs the new `Authorization` with
  the old session id.
- Credential change after a mutating RPC was dispatched → the RPC is
  **not** transparently replayed (fake daemon records at most one
  dispatch); the client surfaces the structured error / unknown-outcome
  path so recovery goes through 2.1 request-id dedup.
- New-CLI-vs-old-daemon remediation: assert the message directs to the
  old executable (`<old bp> disconnect`) or the recorded daemon pid,
  and does **not** instruct a bare `bp disconnect`.
Windows leg (Phase 1.3) runs these. Manual check of the mixed-version UX
with a v0.5.1 CLI against the new daemon before release.

## Phase 5 — Release pipeline

### 5.1 Reorder release jobs around the irreversible step — [compatible]

**Problem.** `release.yml:136-139`: npm publish precedes release-asset
assembly/validation. If `package:agent-plugin` / `package:release-index`
fail, npm is already published with no GitHub Release. Merely swapping the
order would invert the failure mode (public GitHub Release, npm failed).

**Change.** Sequence so both publishes happen only after everything is
validated, and the public release appears only after npm succeeds:

```text
build (matrix)
  → assemble + verify all artifacts (plugin tgz, release index, checksums)
  → create GitHub Release as draft, upload assets
  → npm publish
  → flip the GitHub Release from draft to published
```

If npm publish fails, the draft is invisible to consumers — delete or
retry; nothing irreversible has escaped.

**Re-run semantics (required).** Every step must be idempotent so a
failed run can be re-run whole. The npm artifact needs one authoritative
identity **that survives re-runs**: workflow artifacts cannot provide it
(actions/upload-artifact@v4 artifacts are immutable — a same-name
re-upload fails within a run — and are not automatically visible to a
new run, so a fresh run would silently repack). Instead, the assemble
stage uploads the tgz plus an integrity sidecar (SHA-512) to the **draft
release** before npm publish. Every run — first or re-run — begins by
trying to download the tgz + sidecar from the draft release and
verifying the checksum; only if absent does it run `npm pack` (once) and
upload. Re-running `npm pack` must not be assumed to reproduce the
published bytes — repacking the baseline yields an integrity hash
different from the registry's `dist.integrity` for v0.5.1. The publish
step runs `npm publish <that exact downloaded/packed tgz>`. If the
version is already on the registry, compare
`npm view browser-pilot-cli@<version> dist.integrity` against the
sidecar: match → skip publish and continue to flip the draft (covers
"npm succeeded, draft-flip failed"); mismatch → hard fail for human
investigation. The state machine must also handle **release already
public**: verify npm integrity and asset checksums, then no-op — never
overwrite assets of a published release (draft-stage uploads
overwrite-or-skip; public-stage uploads are forbidden). Concurrency:
serialize per tag
(`concurrency: { group: release-<tag>, cancel-in-progress: false }`).

**Testability.** `workflow_dispatch` on a branch skips the tag-gated
publish steps, so it cannot exercise the draft → npm → finalize state
machine. Put the state machine in a script (e.g.
`scripts/release-publish.mjs`) that takes the `gh` and `npm` commands as
injectable parameters, and unit-test the states — fresh run, npm-done
re-run, integrity mismatch, missing draft, release-already-public
no-op — in
`tests/release-distribution.test.mjs` (or a sibling). The workflow then
just invokes the script; an explicit `--dry-run` flag is an acceptable
complement, not a substitute for the injected-command tests.

Also: handle multiple zips in the notarization step instead of
`-print -quit` taking the first (`release.yml:119`).

**Acceptance.** Exercise the job graph via `workflow_dispatch` on a branch
with publish steps gated on tag refs; `tests/release-distribution.test.mjs`
stays green.
