# Browser Pilot v0.6.1 Backlog

Status: **Open**
Baseline: `v0.6.0` @ `691cb70`
Observation window: 2026-07-31 through 2026-08-07

## Goal

Keep the first patch after v0.6.0 narrow and evidence-driven. The planned work
is CI dependency maintenance. Runtime changes enter v0.6.1 only when release
feedback demonstrates a reproducible defect on a supported configuration.

v0.6.1 must remain backward compatible with v0.6.0. Any protocol change,
declared breaking behavior, or broad feature work moves to a later minor
release.

## Planned maintenance

### 1. Upgrade GitHub Actions runtimes — P1, planned

The v0.6.0 push CI completed successfully, but GitHub annotated each job that
uses `actions/checkout@v4` or `actions/setup-node@v4`: those action versions
target the deprecated Node.js 20 action runtime and are currently being forced
onto Node.js 24.

Scope:

- Move `actions/checkout` and `actions/setup-node` in `ci.yml` and
  `release.yml` to maintained majors backed by the Node.js 24 action runtime.
- Update workflow-policy tests to pin the new action majors without weakening
  their ordering assertions.
- Keep Browser Pilot's own test/build runtime pinned independently to the
  supported Node.js 22 line.

Acceptance:

- Push CI passes `validate`, `windows`, and `browser` with no deprecated
  action-runtime annotations.
- A branch-mode `release.yml` dispatch completes all non-publishing build and
  distribution gates.
- Tag-only npm publishing, GitHub Release publication, and `skill-stable`
  advancement remain gated exactly as in v0.6.0.

## Post-release monitoring

For every report, capture the Browser Pilot version and install channel,
OS/architecture, Node.js version, exact command, structured error code, and the
smallest reproducible sequence. Do not request a daemon token, locator contents,
browser data, or an archive of `BROWSER_PILOT_HOME`.

### 2. Installation and upgrade — P1 when reproducible

Watch for global npm permission failures, an unsupported Node.js version,
multiple `bp` executables on `PATH`, native-archive setup failures, or a managed
skill repeatedly trying to upgrade an already-current CLI.

Action threshold: reproduce the failure on a supported platform with Node.js
22 or later, or identify incorrect installation/preflight guidance. Prefer a
documentation correction for environment-specific setup; change runtime or
packaging behavior only for a product defect.

### 3. Windows ACL startup — P0/P1 depending on reach

Watch for daemon startup failures containing `Cannot restrict Windows ACL`,
especially failures from `whoami.exe` or `icacls.exe` on supported Windows
editions, non-English systems, managed devices, and state directories carried
forward from an older Browser Pilot version.

Action threshold: one reproducible supported-environment startup block or
multiple independent reports with the same command failure. Preserve the
fail-closed security boundary; do not downgrade an ACL failure to a warning
without a replacement access-control guarantee.

### 4. Daemon owner-lock recovery — P0/P1 depending on reach

Watch for `daemon_owner_unverifiable`, an invalid or truncated
`daemon-owner.lock`, or stale-lock removal failures such as `EPERM` and `EBUSY`.
Record whether the owner PID is alive, whether its process-start identity still
matches, and whether the documented lock-file recovery path restores startup.

Action threshold: any permanent startup block not recoverable through the
documented path, a hot loop, or repeated reports caused by normal antivirus or
filesystem behavior. Automatic recovery must continue to require proof that
the recorded owner is dead or has a mismatched process identity.

### 5. Upgrade with an older Broker still running — P1 when unrecoverable

Watch for `protocol_incompatible` when a v0.6.0 CLI encounters a Broker started
by v0.5.x. Confirm that the message identifies the old executable or recorded
daemon PID and that using the old executable to disconnect allows the v0.6.0
CLI to start cleanly.

Action threshold: a user following the emitted remediation cannot recover, the
message recommends bare `bp disconnect`, or the new CLI replaces a live old
Broker automatically. Keep the mixed-version policy fail-closed.

## Triage and release policy

- **P0:** security regression, data loss, uncontrolled browser mutation, or a
  broadly unrecoverable startup failure. Prepare an immediate patch.
- **P1:** reproducible supported-platform block or incorrect recovery contract.
  Fix in v0.6.1 with a regression test and release-note entry.
- **P2:** environment-specific friction with a working recovery path. Improve
  guidance or carry forward with collected evidence.

The Actions runtime upgrade can ship alone after its acceptance gates pass. A
runtime fix must include a regression test and targeted release note. Do not
tag v0.6.1 merely to close monitoring entries with no code or documentation
change.

## Exit criteria

- The Actions runtime upgrade is merged and its CI/release-policy gates pass.
- Reports received during the observation window are classified against the
  thresholds above, with evidence and disposition recorded.
- Any accepted runtime fix passes unit, typecheck, distribution, Windows, and
  browser gates in proportion to its affected surface.
- `docs/releases/v0.6.1.md` describes every shipped user-visible correction
  before a tag is created.

## Initial observation record

- 2026-07-31: v0.6.0 push CI and release workflow completed successfully on
  the first attempt. npm `latest` points to `browser-pilot-cli@0.6.0`, all
  native/plugin assets are public, and `skill-stable` points to `691cb70`.
- 2026-07-31: no post-release installation, Windows ACL, owner-lock, or
  mixed-version recovery reports have been recorded in this backlog yet.

## Explicitly deferred

The pinned same-process iframe DOM-scan and subframe-selector limitations from
the v0.6.0 plan remain deferred. They require a dedicated design and are not
implicitly part of this patch backlog.
